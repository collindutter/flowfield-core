Install the [Codex CLI](https://developers.openai.com/codex/cli/) and sign in.
Make sure `codex` is available in the terminal where you start Flowfield.

## Coordinator Chat

The built-in [Coordinator Chat](/coordinator) uses the same managed ACP runtime as workers.
Install it with `flowfield harness install codex` and choose your model and effort beside
the chat input. Flowfield uses Local automatically; worker delivery configuration can wait.
The service supplies a scoped MCP connection per turn; you do not need to register the standalone connection below for built-in chat.

## Connect a standalone coordinator

With `flowfield serve` running:

```sh
flowfield integration connect codex
flowfield integration status codex
```

Connect verifies the service and saves a native MCP connection in Codex's user settings.
Repeated connections are idempotent. Status checks reachability and tool discovery without
starting a model turn. Other configured MCP connections remain intact.

In your existing project's directory, install its coordinator guidance:

```sh
flowfield project guidance preview
flowfield project guidance install
```

Review and commit adoption files under your project's rules. Start a fresh Codex conversation
in the project, inspect `/mcp`, and ask it to read your Flowfield board. This checks that the
coordinator can actually use the connection and identify the correct project.

## Configure workers

Install the managed runtime with `flowfield harness install codex` (see [runtime installation](/cli#managed-runtime-installation)).
Native Codex must be installed and authenticated on the machine running Flowfield.

Ask the coordinator to configure the project's target branch, dependency setup, verification
and run commands in **Integration** settings, then validate setup. In **Workers**, select a model, reasoning effort and native access mode from the
connected harness. Project defaults can be overridden for individual tasks.

Local uses the tools, credentials and native harness configuration available to the Flowfield
service. Each attempt gets a separate checkout, temporary directory and output directory.
Setup chooses the project's dependency tooling; Flowfield does not create a Python environment.
Use `FLOWFIELD_WORKSPACE` and `FLOWFIELD_RUNTIME_DIR` in reusable setup scripts. Keep databases,
ports and other shared resources separate, or serialize work with one worker slot.

Checks use the service's Local environment. Saved inspection launchers use the terminal's
host environment plus the inspection copy's paths; credentials are never written into them.
Native tool permission requests appear in the task and **Needs you**. Result delivery still
requires explicit approval. Local workspaces protect ordinary parallel edits; they do not
contain arbitrary daemons or isolate the whole machine.

Historical attempts and inspection copies retain their original configuration.
If the service cannot find Codex, restart it from a terminal with the correct PATH, then use
**Reload models**. Installing a bridge does not enable queues.

## Disconnect

```sh
flowfield integration disconnect codex
```

Restart Codex to unload the connection. Project state and saved work remain intact.
For a custom connection name or service port, use the same options for connect, status and disconnect:

```sh
flowfield --port 8770 integration connect codex --name flowfield-local
flowfield --port 8770 integration status codex --name flowfield-local
flowfield --port 8770 integration disconnect codex --name flowfield-local
```
